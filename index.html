NYC Parks has roughly 1.1 million street trees and a growing backlog of hazard reports, but no way to rank which tree gets inspected first — crews work the queue in something close to first-come-first-served order. This is the full build: what each source table actually contains, exactly how they join, the model fit in R using only what this course's Sessions 4–6 actually teach, and what came out when it was run against live data.

TL;DR — for anyone short on time
  • The ask: NYC Parks has ~1.1M street trees and no way to rank hazard reports by actual risk — we built a model that does, using only city data and methods this course teaches.
  • The twist: "Excellent" condition doesn't mean a healthy old tree — it means a newly planted sapling (median 3″ trunk vs. 9–13″ for every other rating), and these young trees are 6× over-represented in the model's highest-risk group. Why is genuinely unresolved — at least 18.8% are confirmed tree replacements (planted after their own hazard report), not proof of sapling fragility.
  • The proof: the model (AUC 0.581) beats both the naive "biggest trees first" heuristic (0.495 — no better than chance) and the city's own existing risk field, catching 1.56× as many real hazard trees as a random sample of the same size would — real, modest, not the 2× first claimed.
  • The catch, disclosed up front: only 36.2% of hazard complaints trace to a specific living tree in the data — a real limitation, stated plainly rather than hidden.
  • The recommendation: flag any planting space with a hazard history for elevated monitoring after every (re)planting — true whether the risk is sapling fragility or something about the location itself.

01

Who's guessing, and what they're guessing at

Every year, NYC's 311 system and Parks Department's own hazard line take in tens of thousands of complaints about street trees — a leaning trunk, a hanging limb, a split at the base. Each complaint becomes a work order in Parks' hazard queue. Today that queue is worked in roughly the order it arrives, not by predicted severity: a genuinely dangerous tree reported on a Tuesday can sit behind a dozen low-risk complaints reported over the weekend.

Two ways to frame the buyer — either works for the presentation:

  1. NYC Parks Dept forestry operations. Reorder the existing hazard queue by predicted risk instead of arrival order, so crews reach the trees most likely to actually fail first.
  2. A property/casualty insurer. Use the same model as a targeting list — which trees near insured buildings are a plausible future claim — to schedule proactive inspection or trim requests, or to price tree-proximity into underwriting.

The insurer framing is the stronger pitch, for a specific reason: the data's blind spot (hazard reports cluster on busy, well-trafficked streets, because someone has to notice and report the tree) is a real limitation for a city trying to be comprehensive across every block — but it's exactly the population an insurer cares about. A tree falling in an empty lot with no reports and no insured structure nearby was never a claim to begin with. That alignment between the data's bias and the buyer's actual loss function is the single biggest reason this beat the other finalists on the shortlist (a Citi Bike rebalancing model and a library-siting model).

Why this fits the rubric

The assignment wants a specific question, a data walkthrough, a clearly explained method, and — flagged as "most important" — actionable implications, for an audience of managers and domain experts. This ends in a literal decision rule, not just a statistic.

02

The three datasets, in detail

All three live on NYC Open Data (data.cityofnewyork.us), queryable through the Socrata API. In R, pull them with httr/jsonlite against the .json endpoint — filter and aggregate server-side with $where/$select/$group wherever possible; never try to download a multi-million-row table whole with read.csv.

1. Forestry Service Requests — mu46-p9is

Parks' own hazard-complaint system ("ForMS 2.0"), not the general public 311 portal. About 86% of its Hazard-category rows originate as 311 calls routed to Parks — this is the correct source table, not the general 311 Service Requests dataset (erm2-nwe9), which turned out to have no usable join key back to a specific tree.

03

The join chain, step by step

There is no exact ID match between the public 311 dataset and the Parks tree system — checked directly: mu46-p9is's complaintnumber looks like a 311 ticket, but the numeric part doesn't match any unique_key in the public 311 dataset. The chain instead runs through Parks' own systems, which do carry a usable location key.

42,675 of 117,739 hazard requests since 2023 (36.2%) trace all the way through to a specific, living, condition-rated tree — this is the real, full-population number; an earlier 180-record sample had estimated a more optimistic ~47%, since superseded. That 42,675 is a count of requests, not distinct trees — since one tree can generate several requests, the actual number of distinct trees this yields is smaller: 14,258 trees with at least one matched hazard report across the full window, of which 7,067 had one specifically before 2025 (the positive class the model was trained on).

Step 1 alone drops the largest share — 45.9% of hazard requests (54,069 of 117,739) never had a physicalid recorded at intake, i.e. the 54.1% figure above is the share that survived, not the drop-off itself. This is unlikely to be random; see Caveats.

04

Results — actually run against live data

Everything above this point is verified data plumbing. Everything below was run end-to-end in R (script: 01_pull_and_model.R) — these are real numbers, not a plan.

The model

glm(hazard_train ~ species_bucket + tpcondition + dbh, family="binomial"), trained on 107,730 living trees (a 10% systematic sample of the tree inventory, plus every hazard-matched tree explicitly backfilled so no positive case was lost to sampling), predicting whether a tree had a hazard report before 2025. Evaluated forward on 100,659 trees that had not yet had a hazard report as of end-2024 — split on time, though not a fully clean holdout: the training table includes the same trees used for evaluation, labelled as negatives, so treat this as a temporally-ordered check rather than a strictly unseen-data test.

Correction

Two things were stated too cleanly in an earlier pass. First: the riskrating row runs on a different, smaller population — only 61% of trees have a rating at all, so 0.533 isn't directly comparable to the other two rows. Recomputed on the shared 61,317-tree subset: full model 0.548, riskrating 0.533, diameter-only 0.528 — the model's edge over the city's own system shrinks to 0.015 on a fair comparison. Real, but modest. Second: ties in the model's predicted scores push the "top decile" cutoff to 13.0% of trees, not 10%, so the fair baseline is a random 13% sample (expected to catch ~937 hazard trees), not a random 10% sample. The actual lift is 1.56×, not 2×.

Honest read

A real, usable lift — not a dramatic one, and smaller than first stated. The headline isn't the raw AUC, it's that the fitted model beats both the naive "biggest trees first" heuristic and the city's own existing risk-rating field, even on a fair like-for-like comparison — just by a narrower margin than a first pass suggested.

The twist: hazard-flagged locations skew toward young trees — the cause is unresolved

Condition does not behave the way intuition suggests, and the pattern itself is real and reproducible:

"Excellent" is not what it sounds like — it isn't the label given to grand, healthy, mature street trees. It's overwhelmingly the label given to newly planted saplings (median diameter 3 inches, versus 9–13 inches for every other condition). These very young trees are roughly 6× over-represented in the model's top-risk group relative to their share of the population. London planetrees show a smaller but real version of the same pattern (species odds ratio 1.46, the single most significant species effect; 23.7% of the top-risk group vs. 10.9% of the population). One small myth-debunk worth a sentence: Callery pears, often assumed structurally weak, actually show a lower hazard odds ratio (0.68×) than the baseline species in this data.

Correction — the cause is genuinely unresolved

An earlier pass stated confidently that this is sapling physical vulnerability — thin trunks, weak roots, exposure to storm and vehicle damage. That's a real possibility, but it isn't the only one, and it hasn't been established. The join links to a planting space (the sidewalk cutout), and condition/size are read from whoever occupies that space today — not necessarily the tree that was there when the hazard was reported. Checked directly against live planting-date records: at least 18.8% of "Excellent" hazard-matched trees were planted after their own hazard report — sometimes 2–3 years after. That's mechanical proof that a meaningful share of "young + hazardous" cases are really "this tree was removed and replaced, and the replacement inherited the address's hazard history." The rest can't be cleanly separated from that same effect using this data or this course's methods — the honest position is that we don't know how much of the pattern is real sapling fragility versus tree turnover, and we're not equipped to find out with what's available here.

The recommendation that survives either way

Rather than betting the recommendation on a cause that isn't settled, aim it at the one thing true regardless of mechanism: a planting space with a hazard history stays elevated risk — whether because a replacement sapling is itself vulnerable, or because something about that location (traffic, exposure, soil) keeps producing problems no matter what's planted there. Any space that has ever generated a hazard report should get an elevated-monitoring flag after every (re)planting, not just checked once and forgotten. That's a genuinely non-obvious recommendation nobody would guess from the dataset's field names alone, and it doesn't require resolving the sapling-vs-replacement question to be worth acting on.

The field rule

As a starting heuristic: any tree under roughly 5 inches in diameter, or sitting in a planting space with a prior hazard report, gets an elevated hazard-monitoring flag; London planetrees carry a standing moderate-priority multiplier regardless of condition. Not yet done: re-running the top-risk-group capture check using only this simplified rule, to confirm it captures most of the same lift as the full model — the next concrete step before this becomes a slide rule rather than a model description.

Still open

Separately from the replacement question: new plantings may also cluster in active construction/streetscape-redesign zones, which independently generate more foot traffic and more 311 calls of every kind — a second, compounding reason condition alone can't be read as a clean health signal. Name both open questions in the presentation rather than picking one.

05

Method

Outcome variable

hazard = 1 if a given tree generated at least one Hazard-category service request in the observation window, 0 otherwise.

Model

model <- glm(
  hazard_train ~ species_bucket + tpcondition + dbh,
  data = train_data,
  family = "binomial"
)

This is the exact formula and exact variable names actually fit — matching the Results section above and the real script in the R Build Plan below. (An earlier version of this page showed a different illustrative formula here, including borough, before the pipeline was finalized — boroughcode was pulled but dropped before the final fit and never appears in any reported number.)

Logistic regression — exactly the method taught in Session 6 (glm(family="binomial"), odds ratios, AIC, confusion matrix). Session 5's factor() dummy-variable approach is implicitly here too, since all three predictors are categorical.

Train/test split: temporal, not random

Train on 2023–24 hazard history, test on 2025–26. A random 70/30 split would let the model "see" outcomes from the same period it's tested on, overstating real-world performance. A temporal holdout proves the model works on trees behaving in a period it never saw — the credibility argument for the whole project.

Benchmark: compare against what the city already does

Report the fitted model's performance next to the naive "prune the biggest trees first" heuristic — and next to Parks' own existing risk field. If the model doesn't clearly beat both, the project doesn't have a story; if it does (it does — see Results), that comparison is the story.

06

Reading the model output

Odds ratios, not raw coefficients

glm()'s raw coefficients are log-odds — convert with exp(coef(model)) and present odds ratios instead. An odds ratio of 2.3 reads as "this tree has 2.3× the odds of a hazard report, holding species and size fixed" — that sentence, not the raw number, belongs on a slide.

Questions to actually ask of the output

  • Which species carry risk beyond what size/condition already explain? Less than hoped, checked directly: species and diameter together add only about 0.003 AUC on top of condition alone (condition-only model: 0.578; full model: 0.581). Condition is doing nearly all the work — species differences (London planetree elevated, Callery pear lower than baseline) are real but small riders on top of it, not an independent finding worth much stage time on their own.
  • Does diameter's effect saturate? It doesn't saturate — it's U-shaped. Checked directly: raw hazard rate is 8.97% for the smallest trees (0–4"), drops to 5.07% for 4–9", then climbs back to 8.32% for 17"+. A single "small tree" flag (dbh under 5") alone scores about as well as the city's own risk-rating field — worth knowing before writing a field rule that assumes risk only rises with size.

Confusion matrix and picking a threshold

0.5 is an arbitrary starting cutoff — hazard events are rare, so a naive 0.5 threshold may flag almost nothing. Pick a threshold (or a top-N cut) that matches the real operational constraint: how many trees can a crew inspect per week.

07

Turning the model into a field rule

The whole point of framing this as decision-shaped rather than claim-shaped is that the output has to be a thing a supervisor can act on without opening R — not a probability, not a p-value.

  1. Score every currently-living tree with the fitted model.
  2. Rank-order by predicted probability.
  3. Find the simplest combination of predictors that approximates the top-decile ranking closely enough to state as a rule.
  4. Validate the rule against the test set, and against the diameter-only benchmark — the rule should sit close to the full model's performance and clearly ahead of the benchmark.

A logistic regression alone is a claim ("this model achieves AUC 0.58"). A field rule is a decision tool — ideas that end in a fact can be argued with; ideas that end in a rule can only be reweighted. That's a much safer position in a 3-minute Q&A.

Implications and recommendations

If the buyer is NYC Parks Dept forestry operations

Today: the hazard queue is worked roughly in arrival order. The ask: crew dispatchers sort the open queue by predicted risk (or apply the field rule directly) before assigning routes — a 1.56× lift in the top-risk group means the same inspection capacity catches more real problems, without needing more crews.

If the buyer is a property/casualty insurer

Today: tree-related claims are handled reactively, after a claim is filed. The ask: the insurer's risk team gets a ranked list of insured addresses with a nearby high-risk tree, used either to request proactive trimming as a loss-prevention condition, or to fold tree-proximity risk into pricing. This is the stronger pitch specifically because the data's bias (over-representing busy, developed streets) is exactly the population an insurer already cares about.

The line for the actual pitch

Weak version: "our model predicts tree hazards." Strong version: "reordering the queue by this model catches 1.56× the hazard trees a same-size random inspection would, beating both the naive size-only heuristic and the city's own risk field — and a hazard location stays elevated risk after every replanting, regardless of what's replanted there."

09

Honest caveats — say these before Q&A finds them

1. The 36.2% yield, and the missing 64% isn't random

The single biggest drop-off is at Step 1 — 45.9% of requests have no physicalid recorded at intake — very unlikely to be random. Plausible mechanism: unaddressed hazards skew toward park-interior trees, not curbside ones. If so, this model really predicts curbside street-tree hazard risk, not city-wide risk — name that scope explicitly.

2. The join is three datasets deep

Heavier plumbing than the two-dataset ideal — an accepted tradeoff for the buyer-aligned bias that makes this idea stand out. Keep the data-walkthrough section of the actual talk tight and visual (a three-box join diagram, not a field-by-field narration).

3. This predicts reported risk, not true structural risk

A dangerous tree that nobody has walked past or reported is invisible to this model — it augments the existing hazard queue, it doesn't replace human observation.

4. Condition ratings are inspector-assessed, not purely objective

Inspection thoroughness varies by district workload. If borough-level patterns show up strongly, be ready to name that as a possible practice artifact rather than asserting it as a real risk difference.

5. The "young tree" twist may partly be tree replacement, not sapling fragility

Condition/size come from a September 2026 snapshot of whoever occupies a planting space today, not necessarily the tree that was there when the hazard was reported. At least 18.8% of "Excellent"-condition hazard-matched trees were planted after their own hazard report — confirmed replacements. The rest can't be cleanly separated from that same effect. See Results for the full explanation and the recommendation that sidesteps needing to resolve it.

6. The modeling population is enriched with cases, not a clean random sample

The 107,730-tree training population is a 10% systematic sample of the inventory plus every hazard-matched tree added back in, so hazard prevalence in the modeling data (13.23%) is far higher than the true city-wide rate (roughly 1–2%). This leaves the odds ratios valid (case-control sampling doesn't bias them), but it means the predicted probabilities and the "top 13%" cutoff do not directly generalize to ranking all 1.1M real trees without re-calibration — flag this if asked how the field rule would actually be deployed at full scale.

Anticipated Q&A, answered in advance

  • "Why not the 2015 Street Tree Census — it's more complete?" — It's a one-time historical snapshot, last touched 2017; the live Tree Points table is the actual current inventory.
  • "Isn't 'bigger, unhealthier trees are riskier' obvious?" — It's not even true in this data: hazard rate by diameter is U-shaped (high for the smallest trees, dips in the middle, rises again for the largest), and condition doesn't rank the way you'd expect either — "Excellent" carries the highest odds ratio of any condition, not the lowest.
  • "So are young trees actually more dangerous, or not?" — Honestly unresolved. At least 18.8% of the "Excellent" hazard trees are confirmed replacements planted after their own hazard event; the rest can't be cleanly separated from that same effect with this data. Say this plainly rather than picking a side the data doesn't support.
  • "What happens to the 64% you couldn't match?" — Answered directly in caveat 1: named as scope (curbside trees), not silence.

R build plan

Packages: httr, jsonlite, dplyr, pROC. Two real bugs worth knowing if you extend this script: R silently formats large offsets like 100000 as 1e+05 in a URL unless options(scipen=999) is set — Socrata rejects it; and Socrata's .json endpoint only accepts POST for writes (it demands auth) — reads must use GET.

## Run: Rscript 01_pull_and_model.R
## Writes intermediate CSVs to this folder + prints all results to stdout.

options(scipen = 999)  # otherwise large offsets like 100000 get sent as "1e+05" and Socrata rejects them

suppressMessages({
  library(httr)
  library(jsonlite)
  library(dplyr)
})

BASE <- "https://data.cityofnewyork.us/resource/"

soql_get <- function(dataset_id, select, where = NULL, page_size = 50000, max_pages = 40) {
  out <- list()
  offset <- 0
  repeat {
    params <- list(`$select` = select, `$limit` = page_size, `$offset` = offset)
    if (!is.null(where)) params[["$where"]] <- where
    page <- NULL
    backoffs <- c(5, 10, 20, 30, 45, 60, 60, 60)
    for (attempt in seq_along(backoffs)) {
      resp <- tryCatch(
        GET(paste0(BASE, dataset_id, ".json"), query = params, timeout(180),
            add_headers(`User-Agent` = "mbacourse-tree-project/1.0")),
        error = function(e) NULL
      )
      if (!is.null(resp) && status_code(resp) == 200) {
        page <- fromJSON(content(resp, as = "text", encoding = "UTF-8"), flatten = TRUE)
        break
      }
      body_snippet <- if (!is.null(resp)) substr(content(resp, as = "text", encoding = "UTF-8"), 1, 300) else "no response"
      cat(sprintf("  (retry %d for %s offset %d, status %s, waiting %ds) body: %s\n",
                  attempt, dataset_id, offset, if (is.null(resp)) "NA" else status_code(resp),
                  backoffs[attempt], body_snippet))
      Sys.sleep(backoffs[attempt])
    }
    if (is.null(page)) stop(sprintf("Failed to pull %s at offset %d after %d attempts", dataset_id, offset, length(backoffs)))
    if (length(page) == 0 || nrow(page) == 0) break
    out[[length(out) + 1]] <- page
    cat(sprintf("  %s: pulled %d rows (offset %d)\n", dataset_id, nrow(page), offset))
    if (nrow(page) < page_size) break
    offset <- offset + page_size
    if (offset / page_size >= max_pages) break
    Sys.sleep(1.5)
  }
  if (length(out) == 0) return(data.frame())
  bind_rows(out)
}

    where_clause <- sprintf("plantingspaceglobalid in (%s)", id_list)

                      select = "plantingspaceglobalid,genusspecies,dbh,tpcondition,riskrating",
                      where = where_clause, page_size = 500, max_pages = 1)
    if (i %% 20 == 0) cat(sprintf("  missing-tree batch %d/%d: got %d rows so far this batch\n", i, length(chunks), nrow(part)))
    if (nrow(part) > 0) extra_tree_rows[[length(extra_tree_rows) + 1]] <- part
    Sys.sleep(0.3)
  }
  if (length(extra_tree_rows) > 0) {
    write.csv(bind_rows(extra_tree_rows), "raw_extra_tree_rows.csv", row.names = FALSE)
  }
}
force_char <- function(df) {
  if (nrow(df) == 0) return(df)
  df %>% mutate(across(everything(), as.character))
}
if (length(extra_tree_rows) > 0) {
  tree_all <- bind_rows(force_char(tree_sample), force_char(bind_rows(extra_tree_rows)))
} else {
  tree_all <- force_char(tree_sample)
}
tree_all <- tree_all %>% distinct(plantingspaceglobalid, .keep_all = TRUE)
cat(sprintf("Combined tree population for modeling: %d rows\n", nrow(tree_all)))

## --- 5. Restrict to living trees with a recorded condition (steps 3/5 of join chain) ---
tree_alive <- tree_all %>%
  filter(!is.na(tpcondition), !tpcondition %in% c("Dead", "Unknown"))
cat(sprintf("Living trees with recorded condition: %d (dropped %d dead/unknown/blank)\n",
            nrow(tree_alive), nrow(tree_all) - nrow(tree_alive)))

## --- 6. Attach hazard outcome + dates to the modeling population ------------------
model_data <- tree_alive %>%
  left_join(hazard_globalids_dates, by = c("plantingspaceglobalid" = "globalid")) %>%
  mutate(
    dbh = as.numeric(dbh),
    riskrating = suppressWarnings(as.numeric(riskrating)),
    hazard_ever = ifelse(is.na(first_hazard_date), 0, 1)
  )

cat(sprintf("\nOverall hazard prevalence in modeling population: %d / %d = %.2f%%\n",
            sum(model_data$hazard_ever), nrow(model_data), 100 * mean(model_data$hazard_ever)))

## bucket species to top 10 + Other (hundreds of rare species otherwise)
top_species <- model_data %>% count(genusspecies, sort = TRUE) %>% slice_head(n = 10) %>% pull(genusspecies)
model_data <- model_data %>%
  mutate(species_bucket = ifelse(genusspecies %in% top_species, genusspecies, "Other"))

## --- 7. Temporal design: train on 2023-24 outcomes, test forward on 2025-26 -------
## "at risk as of end of 2024" = had NOT already had a hazard report before 2025-01-01
cutoff <- as.Date("2025-01-01")
model_data <- model_data %>%
  mutate(
    hazard_train = ifelse(!is.na(first_hazard_date) & first_hazard_date < cutoff, 1, 0),
    at_risk_end_2024 = ifelse(is.na(first_hazard_date) | first_hazard_date >= cutoff, TRUE, FALSE),
    hazard_test = ifelse(!is.na(first_hazard_date) & first_hazard_date >= cutoff, 1, 0)
  )

train_data <- model_data  # fit on the full population's 2023-24 outcome
test_data  <- model_data %>% filter(at_risk_end_2024)  # only trees not already flagged pre-2025

cat(sprintf("Train rows: %d (hazard_train prevalence %.2f%%)\n",
            nrow(train_data), 100 * mean(train_data$hazard_train)))
cat(sprintf("Test rows (still at risk as of end of 2024): %d (hazard_test prevalence %.2f%%)\n",
            nrow(test_data), 100 * mean(test_data$hazard_test)))

train_data$tpcondition <- relevel(factor(train_data$tpcondition), ref = "Good")
test_data$tpcondition  <- factor(test_data$tpcondition, levels = levels(train_data$tpcondition))
train_data$species_bucket <- factor(train_data$species_bucket)
test_data$species_bucket  <- factor(test_data$species_bucket, levels = levels(train_data$species_bucket))
train_data$boroughcode <- NULL  # not on tree_points; borough dropped from this cut (see notes)

## --- 8. Fit the full model + the diameter-only benchmark -------------------------
full_model <- glm(hazard_train ~ species_bucket + tpcondition + dbh,
                   data = train_data, family = "binomial")
benchmark_model <- glm(hazard_train ~ dbh, data = train_data, family = "binomial")

cat("\n=== FULL MODEL: odds ratios ===\n")
print(round(exp(coef(full_model)), 3))

cat("\n=== FULL MODEL: summary ===\n")
print(summary(full_model))

## --- 9. Evaluate forward on the temporal holdout ----------------------------------
test_data$pred_full      <- predict(full_model,      newdata = test_data, type = "response")
test_data$pred_benchmark <- predict(benchmark_model,  newdata = test_data, type = "response")

if (!requireNamespace("pROC", quietly = TRUE)) install.packages("pROC", repos = "https://cloud.r-project.org")
library(pROC)
roc_full <- roc(test_data$hazard_test, test_data$pred_full, quiet = TRUE)
roc_bench <- roc(test_data$hazard_test, test_data$pred_benchmark, quiet = TRUE)
cat(sprintf("\nAUC, full model on 2025-26 holdout:      %.3f\n", auc(roc_full)))
cat(sprintf("AUC, diameter-only benchmark on holdout:  %.3f\n", auc(roc_bench)))

## --- 10. Existing Parks risk rating, as a second benchmark (bonus finding) --------
has_rr <- test_data %>% filter(!is.na(riskrating))
if (nrow(has_rr) > 50) {
  roc_rr <- roc(has_rr$hazard_test, has_rr$riskrating, quiet = TRUE)
  cat(sprintf("AUC, Parks' own existing riskrating field: %.3f (n=%d with a rating)\n",
              auc(roc_rr), nrow(has_rr)))
}

## --- 11. Top-decile field-rule extraction -----------------------------------------
cutoff90 <- quantile(test_data$pred_full, 0.9, na.rm = TRUE)
top_decile <- test_data %>% filter(pred_full >= cutoff90)
cat(sprintf("\nTop-decile risk cutoff (predicted prob): %.4f\n", cutoff90))
cat(sprintf("Top-decile capture rate of actual 2025-26 hazard trees: %d / %d = %.1f%%\n",
            sum(top_decile$hazard_test), sum(test_data$hazard_test),
            100 * sum(top_decile$hazard_test) / sum(test_data$hazard_test)))
cat("Top-decile composition (species x condition):\n")
print(top_decile %>% count(species_bucket, tpcondition, sort = TRUE) %>% slice_head(n = 10))

conf_mat <- table(predicted = ifelse(test_data$pred_full >= cutoff90, 1, 0),
                   actual = test_data$hazard_test)
cat("\nConfusion matrix at top-decile threshold:\n")
print(conf_mat)

## --- save everything for reference -------------------------------------------------
saveRDS(list(full_model = full_model, benchmark_model = benchmark_model,
             train_data = train_data, test_data = test_data),
        "model_results.rds")
write.csv(model_data, "final_modeling_table.csv", row.names = FALSE)
cat("\nDone. Saved model_results.rds and final_modeling_table.csv\n")
